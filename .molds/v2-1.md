# Checking codebase for bugs and errors

## TL;DR

- **High:** `sys.ecit` typo crashes `--all` mode in batch_contact_imports.py; LLM `None` content crashes classify pipeline; `get_journey_intent_results_by_tenant` returns tuple on error but caller checks for string (error undetected, downstream crash)
- **Medium:** OpenAI classifier uses `intent_label` key but Gemini/Anthropic use `journey_stage` (cross-provider mismatch); `json.JSONDecodeError` uncaught in all LLM parsers; batch counter reset per loop; silent `except: pass` swallows version-lookup errors; `save_classifier_draft` returns active config not the saved draft; Activate button activates stale DB version when user has unsaved edits; `"now()"` sent as string literal not timestamp
- **Low:** dead `if not contacts_resp: break` guard; dead slug re-check; classify_worker import path breaks `python -m scripts.classify_worker`

## Problem

A full read of all files found 10 confirmed bugs (3 high, 7 medium) and 4 low-severity issues.
Several subagent claims were discarded after reading the code:
- H2 (PID not stored in Home.py) — `batch_messages_import.py:211-213` writes its own PID to DB; grace period handles the race. NOT a bug.
- M8 (silver skipped when insert_count non-int) — `insert_bronze_messages` always returns int on success; the `isinstance` guard is dead but causes no real harm.

## Solution

Fix in order of severity. Each fix is targeted to one file.

### High severity

**H1. `batch_contact_imports.py:189` — `sys.ecit` typo (AttributeError crash)**
```python
for tenant in tenants:
    sys.ecit(run_contact_imports(tenant["tenant_id"]))   # ← typo crashes immediately
```
`sys.ecit` does not exist; running `--all` raises `AttributeError: module 'sys' has no attribute 'ecit'` on the first tenant. Fix: `sys.exit(run_contact_imports(...))`.

**H2. `llm_apis.py` — `response.choices[0].message.content` can be `None`**
The `if response == None` guard (lines 113, 181, 260) checks the response **object**, which is always truthy (the SDK raises exceptions, it doesn't return `None`). The real risk is `response.choices[0].message.content` being `None` (content-filter refusals, tool-call responses). `_strip_markdown_fences` then calls `text.strip()` → `AttributeError: 'NoneType' has no attribute 'strip'`, burning all retries.
Fix: after extracting `content`, add `if content is None: raise ValueError("LLM returned null content")` in all three classifiers.

**H3. `database.py:181` — `get_journey_intent_results_by_tenant` returns tuple on error; caller checks for string**
```python
# database.py:181
except Exception as e:
    return f"Error fetching intent journey results: {e}", False   # tuple!

# 1_Journey_Analytics.py:82
if isinstance(data, str):   # tuple is not str → always False → error undetected
    st.error(data)
    st.stop()
```
When the DB call fails, `data` is a tuple `(str, False)`. The `isinstance(data, str)` check is False so the page continues, then crashes when iterating `data` (a tuple) as a list. Fix: return only the string on error (no tuple), matching how `get_contact_activity_by_tenant` handles errors (returns `[]`).

### Medium severity

**M1. `llm_apis.py` — `json.JSONDecodeError` uncaught in all three classifiers**
Lines 117, 186, 264 call `json.loads(...)` without catching `json.JSONDecodeError`. When the LLM returns malformed JSON (common), this propagates uncaught through `classify_contact_with_retry`, burning all 3 retries on the same bad output (temperature 0.1 → same response each time).
Fix: wrap `json.loads` in a try/except and raise `ValueError` so the retry counter increments with a meaningful message. Log the raw content.

**M2. `llm_apis.py` — cross-provider JSON key inconsistency**
OpenAI system prompt asks for `"intent_label"` (line 99) and extracts `parsed.get("intent_label", labels[0])` (line 119). Gemini and Anthropic ask for `"journey_stage"` and extract `parsed.get("journey_stage", ...)`. If you switch providers, classification silently falls back to `labels[0]` because the JSON key is wrong.
Fix: standardise all three providers to `"journey_stage"`. Update the OpenAI system prompt template (line 99) and key extraction (line 119).

**M3. `classify_worker.py:54-55` — succeeded/failed counters reset each loop iteration**
```python
while True:
    ...
    succeeded = 0   # ← reset every iteration
    failed = 0
    ...
print(f"  Summary: {succeeded} classified, {failed} failed")  # only last batch
```
`succeeded` and `failed` are reinitialised at the top of the `while True` loop. The summary only reflects the last batch.
Fix: initialise both counters once before the `while True:` loop.

**M4. `orchestrator.py:259` — silent `except: pass` swallows version-lookup errors**
```python
except Exception:
    pass   # no log, no warning
```
Any DB/auth failure fetching the active config version silently leaves `active_version = _FALLBACK_VERSION` (1), disabling version-drift detection without any trace.
Fix: `except Exception as e: print(f"Warning: could not fetch active config version: {e}")`.

**M5. `database.py:298,537` — `"now()"` sent as string literal**
`create_import_job` and `mark_job_completed`/`mark_job_failed` all set timestamps as the string `"now()"`. PostgreSQL recognises `'now'` as a valid timestamptz input but NOT `'now()'` (parentheses make it unrecognised as a datetime literal, stored as-is or error depending on strict mode). The column likely has a server-side default so in practice the import mostly works, but `completed_at` and `started_at` could be wrong.
Fix: use `datetime.utcnow().isoformat() + "Z"` or omit the field and rely on the DB default where one exists. Same fix needed in `upsert_sync_progress:587` for `"updated_at": "now()"`.

**M6. `database.py:868` — `save_classifier_draft` returns active config, not the saved draft**
```python
return get_active_classifier_config(tenant_id)[0] or {"config_id": config_id}, True
```
After saving a draft, the function returns the **active** config. If there is no active config, it returns `{"config_id": config_id}` losing stage data. Callers in Settings.py don't use the return value (just check `ok`), so this doesn't cause a visible crash, but it is semantically wrong and could break future callers.
Fix: return the saved draft's data by reading it back: `return get_draft_classifier_config(tenant_id)[0], True`.

**M7. `2_Settings.py:346` — Activate button activates the last saved DB draft, losing in-memory edits**
The Activate button is gated on having run a test (correct), but activation calls `activate_classifier_config(tenant_id, draft_config["config_id"])` using whatever is stored in DB, ignoring any edits in `draft_prompt` and `edited_stages_df` made since the last save. The user may have edited and tested, but activation picks up the pre-edit DB state silently.
Fix: save the draft first, then activate:
```python
_, save_ok = save_classifier_draft(tenant_id, draft_prompt, edited_stages_df.to_dict("records"), draft_notes or None)
if save_ok:
    _, ok = activate_classifier_config(tenant_id, draft_config["config_id"])
```

### Low severity (fix opportunistically)

- **`orchestrator.py:236`** — `if not contacts_resp: break` — Supabase response objects are always truthy; this guard is dead. Correct check is `if not contacts_resp.data:`. No crash in practice because line 239 `if len(contacts_resp.data) < page_size: break` terminates pagination correctly.
- **`database.py:68`** — `tenant.data[0]["slug"] != slug` is always False since the query already filters by `.eq("slug", slug)`. Dead code; remove the slug part of the condition, keep the password check.
- **`database.py:149`** — `response.data[0]` with no length check; empty result raises `IndexError` caught by `except Exception` with a confusing "list index out of range" message. Add `if not response.data: return "Contact not found", False`.
- **`classify_worker.py:19`** — `from classifiers.factory import get_classifier` is a bare import that requires `scripts/` to be on `sys.path`. When run as `python -m scripts.classify_worker` from the project root, `scripts/` is NOT on `sys.path`, only the project root is. The script likely only works when run as `python scripts/classify_worker.py` from root (which adds `scripts/` as cwd). Fix: add `sys.path.insert(0, str(Path(__file__).parent))` at the top, matching the pattern in `batch_messages_import.py`.
